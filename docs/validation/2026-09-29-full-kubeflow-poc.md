## Repeatability and remaining limits

- A repeat approved Kubeflow apply succeeded. Read-only `kubectl diff` still reports 17 objects, mainly aggregated ClusterRole rules and admission webhook CA/rules/failure-policy fields maintained by controllers; one NetworkPolicy difference was only its generated `metadata.generation`. Treat this as a documented drift-report limitation, not a zero-drift result. The 60-object workload/PVC readiness check passed.
- Ansible preflight passed on both hosts before installation with zero changes. A post-install repeat without a sudo password stopped at the root-owned K3s environment guard with zero changes; repeat privileged Ansible idempotency is not verified. Teardown and repeat teardown were not run because the customer requested the PoC remain available.
- The unused `ubuntu` cache PVC can remain Pending with `WaitForFirstConsumer`; the `vis-lab` PVC bound and served the successful run. Host cache file-inventory fingerprints matched immediately before and after the binding apply. Training may legitimately update local model-cache files afterward.
- The KFP 2.16.1 public PVC extension does not expose read-only mounts. Unlike the previous Argo Pod template, the PoC KFP cache subpath mounts are writable. The run did not intentionally modify dataset data, but this protection gap should be resolved before treating the pipeline as production-ready.
- The localhost forward runs as a transient user systemd service. It survives this chat but must be restarted after a host reboot. `systemctl --user status labclip-kubeflow-local-ui.service` shows its state; `systemctl --user stop labclip-kubeflow-local-ui.service` stops only the local UI forward, not Kubeflow.

The cluster, Kubeflow, MinIO data, and W&B records were left running/intact. Teardown remains a separate reviewed action.
